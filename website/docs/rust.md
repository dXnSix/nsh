# Building with Rust

Native Shell apps are written in Rust, in TSX, or in both. All three run on the same engine: the reactive graph, the
renderer, Taffy layout and the native modules (navigation, dialogs, the keyboard, the status bar) are Rust in every case, and every platform renders with its
own UI. What differs is the language of your own code, and with it whether the app carries a JavaScript VM.

| | Rust | TSX | Rust with TSX |
|---|---|---|---|
| Your UI, state and handlers | Rust | TSX on QuickJS | Rust components and modules, TSX screens that use them |
| The app runs | the engine and your crate only, on every platform and in the browser | QuickJS and the engine (in the browser, its JavaScript engine) | QuickJS and the engine, with your crate (in the browser, its JavaScript engine) |
| Suits | Medium and large apps with demanding business logic | Apps and modules delivered at run time, quick iteration | A Rust core with parts that change often |
| Edits | Rebuild and restart | Hot updates | Hot updates for TSX, rebuild and restart for Rust |
| Start | `nsh init my-app --template rust` | `nsh init my-app --template ts` | `nsh init my-app --template mixed` |

## Choosing

**Rust** suits apps whose business logic is large and demanding: trading, editors, data-heavy tools. You get Rust's
type system and compile-time checks across the whole app, the crates.io ecosystem, native performance for your own
code (not only for NSH's), and headless tests of the real UI with `cargo test`. The app is Rust and native code from
start to end: no JavaScript VM ships with it or runs in it, on iOS, Android, macOS, Windows, Linux, GPUI and the web.
Components are functions that run once and bind signals to what they show, as in TSX ([Reactivity](./reactivity.md)),
written with typed styles instead of class strings.

**TSX** suits UI that arrives after the app ships: modules a native app loads at run time, generated by a model or
written by another team, delivered as [signed packages](./signed-packages.md) and run in a sandbox the host configures,
with hot updates while you develop.

**Rust with TSX** keeps the Rust core and adds TSX where it pays off: screens, settings, onboarding, experiments,
anything you iterate on with hot updates or deliver at run time as a [signed package](./signed-packages.md). TSX
imports your Rust components and modules like any NSH module, so the two halves meet at typed interfaces. The TSX
runs on QuickJS, which the app then carries.

## An app written in Rust

```sh
nsh init my-app --template rust
cd my-app
nsh run                        # this machine's backend; --target ios, android, web, macos, linux or windows
nsh package --target web       # or ios, ios-simulator, android, macos, linux, windows
```

Build with [huacnlee/cargo](https://github.com/huacnlee/cargo), the Cargo NSH is developed with: a drop-in fork that builds each dependency once for all your
projects and Git worktrees and keeps its build directory under a size limit on its own, with nothing to configure
([Installation](./installation.md#for-apps-written-in-rust)).

`src/lib.rs` holds the app: components, state, handlers, tasks.

```rust
use nsh_base::{button, theme};
use nsh_core::prelude::*;

/// The components available to TSX through `app/native`.
#[native_module("app/native")]
fn native(registry: &mut Registry) {
    registry.register::<App>();
}

#[component]
pub fn App() -> impl IntoElement {
    let count = signal(0_u32);
    let quote = signal(SharedString::from("…"));
    // Async work runs in tasks; requests go through NSH's network stack.
    spawn(async move {
        if let Ok(response) = fetch("https://api.example.com/quote").await {
            quote.set(response.text().into());
        }
    });
    view()
        .flex_1()
        .items_center()
        .justify_center()
        .gap_4()
        .child(text(move || format!("Count: {}", count.get())))
        .child(text(quote))
        .child(
            // nsh_base's unstyled button, drawn with the theme's colors.
            button()
                .px(px(20.0))
                .py(px(12.0))
                .rounded(move || theme().radius)
                .bg(move || theme().primary)
                .active(|s| s.bg(move || theme().primary.opacity(0.9)))
                .on_press(move || count.update(|c| *c += 1))
                .child(text("Tap").text_color(move || theme().primary_foreground)),
        )
}
```

Elements and components are made the same way: a function makes one (`view()`, `text(..)`, `nsh_base`'s
`button()`, your `#[component] fn Chart`'s `chart()`), and its methods set its props, one setter per prop (a value,
a signal or a closure), and its listeners, one method per event. Listeners are closures of their event
(`move |text: &str| ..`), and `move || ..` for an event without data; `.child(..)` takes an element, or an
`Option`, a `Vec`, an array or an iterator of elements (`.child(rows.iter().map(|r| row(r)))`).

`nsh.json` names the root, and `nsh` mounts it:

```json
{
  "name": "My App",
  "rust": ".",
  "root": "App",
  "theme": "theme.json",
  "appearance": "system"
}
```

`"root"` is the component's path in the crate (`App`, `shell::Gallery`; in the first one with
[several crates](#several-crates)); `"theme"` is the [theme](#theme) its components draw with, and `"appearance"` applies to it as it does to a TSX app. With it,
`nsh run` and `nsh package` of the app's directory build the app's own runner for the target, with the root mounted
and no QuickJS linked in:

| Target | What runs |
|---|---|
| macOS, Windows, Linux | The release runner with your crate, in a window; `nsh run` runs a debug build and shows the app's logs in the terminal |
| iOS, the iOS simulator, Mac Catalyst | The iOS runner with your crate, in an app |
| Android | The app's `libnsh.so` with your crate, started by the runtime's activity |
| Web | `nsh.wasm` with the engine and your crate (3.3 MB for the whole Rust gallery, 0.75 MB with brotli); the page mounts the root |

`nsh` builds what your crate needs and nothing more: a small program of your crate and NSH's core that describes its
components and modules to the CLI, which then does the rest itself, and the runner of each target you run or
package. The first build of a new Rust app compiles your crate and NSH's core, about 60 crates. `nsh test` runs
the app's tests headless in a runner of your crate built the same way.

On Linux, your crate selects optional platform features. Enable `webview` on your
`nsh-platform-linux` dependency to use web views; this links WebKitGTK 6.0, which must be installed to build and run
the app. The generated runner inherits that choice through Cargo feature unification.

During `nsh run`, a change to the crate's Rust code builds the runner again and restarts the app; in the browser,
the open page loads the new runtime by itself. `cargo run` starts the same root directly on the desktop backend
(`src/main.rs`), and native apps that embed NSH mount a Rust root with `AppSource::Rust` on the `AppView` of macOS,
Windows, Linux, GPUI and iOS.

Code for every platform, the web included, uses NSH's services: `fetch` for HTTP
([Networking](./networking.md#from-rust-components)), `timer`, `set_timeout` and `set_interval` for waiting,
`nsh_core::time::Instant` and `nsh_core::time::unix_ms()` for the clock. `background` and `blocking` run work on the
native targets' threads. `run_on_main_thread(f)` runs `f` on the platform's main thread, for APIs that only work there
(AppKit's status items, UIKit): after the views of the current turn are mounted, and its result is a future to await
on the engine thread. A module function that is not `async` calls `cx.run_on_main_thread(f)`. On the web and in
headless tests `f` runs on the engine thread at the end of the commit, and on the native platforms later, while the
engine goes on: await the result to know that `f` ran. `f` returns a value, and the code that awaits it writes signals
and calls NSH's functions with it.

## Desktop title bars

Rust apps draw their own title bars with `nsh_core::element::desktop`. Set the
window's `title_bar` attribute to `TitleBarStyle::Hidden` with
`current_window().set(..)`, mark the bar's background
with `.window_drag(true)`, and reserve the native window controls' space with
`title_bar()`. Its `top` is the bar's height, and `left` and `right` are the widths
occupied by the system controls. Reading it subscribes to changes, including full
screen. The platform handles window dragging and the user's title-bar double-click
behavior; `.window_drag(false)` keeps a child out of its parent's drag region.

```rust
use nsh_core::{
    desktop::{TitleBarOptions, TitleBarStyle, WindowAttributes, WindowControl},
    element::desktop::{current_window, title_bar},
    prelude::*,
};

fn window_bar() -> impl IntoElement {
    let mut bar = TitleBarOptions::default();
    bar.style = TitleBarStyle::Hidden;
    bar.height = Some(px(42.0));
    let mut attributes = WindowAttributes::default();
    attributes.title_bar = Some(bar);
    current_window().set(attributes);
    view()
        .h(px(42.0))
        .flex_row()
        .items_center()
        .window_drag(true)
        .pl(move || title_bar().left + px(12.0))
        .pr(move || title_bar().right + px(12.0))
        .child(text("My app").flex_1())
        .child(text("Close").window_control(WindowControl::Close))
}
```

A title bar with `TitleBarStyle::Default` restores the system's. A view with
`.window_control(..)` is the window's minimize, maximize or close button: the
platform carries out its press, and a close goes through the window's
`close_on_press`. The `WindowRef` has the window's other requests
(`set_mode`, `minimize`, `set_bounds`, `close`, ...), `window()` opens windows of
the app's own, and the module has the menus (`set_application_menu`,
`popup_menu`) too: [nsh/desktop](../modules/nsh-desktop.md).

## Files and folders

On the desktops, Rust code shows the system's file dialogs and hands local paths to
the system, each answer awaited in a task: `pick_paths` with an `OpenDialog`
(`OpenDialog::files()`, `::folders()` or `::files_and_folders()`), `pick_save_path`
with a `SaveDialog`, `open_path` (the file's default app), `reveal_path` (the item
selected in Finder, File Explorer or the file manager) and `move_to_trash` (where the
item went, when macOS says). The dialogs answer `Ok(None)` when the user cancels and
an error when they cannot show (on Linux without a file chooser portal, and on iOS,
Android and the web, where `open_path`, `reveal_path` and `move_to_trash` answer
an error too). Every request that fails answers its error, never `false`.

```rust
use nsh_core::{
    file_dialog::{FileFilter, OpenDialog},
    prelude::*,
};

fn open_notes() {
    let picked = pick_paths(
        OpenDialog::files()
            .multiple(true)
            .filter(FileFilter::new("Markdown", ["md", "markdown"]))
            .button_label("Open"),
    );
    spawn(async move {
        match picked.await {
            Ok(Some(paths)) => {
                for path in paths {
                    let _ = reveal_path(path).await;
                }
            }
            Ok(None) => {} // Cancelled.
            Err(error) => log::warn!("no file dialog: {error}"),
        }
    });
}
```

## Signing in on the web

`open_auth_session` opens a provider's sign-in page (an OAuth authorization URL) and
answers with the callback URL it redirects to: iOS shows it in an
`ASWebAuthenticationSession` sheet (`.ephemeral(true)` keeps it apart from the user's
Safari data), Android in a Custom Tab, other platforms in the system browser. Outside
iOS the callback comes back as a link of a scheme the app claims (`nsh.json`
`schemes`); the session takes it, so `next_url_scheme_open` never hears it. The
answer is `Completed(url)` or `Cancelled` (the user closed the page or came back to
the app without signing in); a session with nothing to bring its callback back fails
with `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`. The page's URL needs the `openUrl`
capability, as `open_url` does.

When the app learns the user signed in some other way while the page still shows (a
device code approved on a page that never redirects back), `close_auth_session()`
closes it: the session answers `Cancelled`, and iOS and Android take the page away and
bring the app back. A page in a desktop browser stays open. With no session waiting,
it does nothing.

```rust
use nsh_core::{
    auth_session::{AuthSessionOutcome, AuthSessionRequest},
    prelude::*,
};

fn sign_in(authorize_url: String) {
    let session = open_auth_session(AuthSessionRequest::new(authorize_url, "myapp"));
    spawn(async move {
        match session.await {
            Ok(AuthSessionOutcome::Completed(callback)) => log::info!("signed in: {callback}"),
            Ok(_) => {} // Cancelled.
            Err(error) => log::warn!("no sign-in page: {error}"),
        }
    });
}
```

In tests, `Headless::on_auth_session` gives the platform an in-app session and ends
each one with the outcome given, and `keep_auth_sessions_open` leaves each one open
until the app closes it (`screen().auth_session_showing()`); without either the page
is in `opened_urls()` and `open_with_url` delivers the callback.

## Extending a Rust app with TSX

The crate's `#[native_module("app/native")]` function names what TSX may import: components
(`registry.register::<Chart>()`), modules of functions (`registry.module::<Portfolio>()`, `#[module]` on a unit struct and its `impl`),
classes (`registry.class::<Ledger>()`, `#[class]` on a struct and its `impl`) and assets; the attribute also makes
`pub fn registry()` at the crate's root, the same set for your tests and other Rust code (`my_app_native::registry()`,
next to `nsh_base::registry()`). In a `#[module]` or
`#[class]` `impl`, the `pub fn`s are exported (`pub(crate)` too); functions without a visibility are helpers that
stay in Rust. Their TypeScript
declarations, doc comments included, are generated from the Rust types into `.nsh/types`, so TSX is checked against
them by `nsh check` and your editor:

```rust
/// A price chart.
#[derive(Clone, PartialEq, Props)]
pub struct ChartProps {
    /// The symbol to chart.
    pub symbol: Prop<SharedString>,
    /// The range shown.
    #[prop(default = SharedString::from("1D"))]
    pub range: Prop<SharedString>,
}

#[derive(Event)]
pub enum ChartEvent {
    /// A price was selected.
    #[args(price)]
    Select(f64),
}

/// A price chart; a press selects the last price.
#[component]
pub fn Chart(props: ChartProps, cx: Scope<ChartEvent>) -> impl IntoElement {
    view()
        .h(px(160.0))
        .bg(move || theme().muted)
        .on_press(move || cx.emit(ChartEvent::Select(101.5)))
        .child(text(move || format!("{} · {}", props.symbol.get(), props.range.get())))
}

/// A ledger kept in Rust.
#[class]
pub struct Ledger {
    entries: Vec<f64>,
}

#[class]
impl Ledger {
    /// An empty ledger.
    pub fn new() -> Self {
        Ledger { entries: Vec::new() }
    }

    /// Adds `amount`; the new balance.
    pub fn add(&mut self, amount: f64) -> f64 {
        self.entries.push(amount);
        self.balance()
    }

    /// The balance.
    #[getter]
    pub fn balance(&self) -> f64 {
        self.entries.iter().sum()
    }

    /// Uploads the entries; resolves when the server has them.
    pub async fn upload(this: Instance<Ledger>, url: String) -> Result<(), String> {
        let body = this.with(|l| format!("{:?}", l.entries));
        fetch(HttpRequest::post(url, body)).await.map(|_| ())
    }
}

/// The app's holdings.
#[module]
pub struct Portfolio;

#[module]
impl Portfolio {
    /// The value of the holdings.
    pub fn total() -> f64 {
        1250.0
    }
}
```

```tsx
import { mount, signal, View, Text } from "nsh";
import { Window } from "nsh/desktop";
import { Chart, Ledger, Portfolio } from "app/native";   // Rust

const ledger = new Ledger();   // its state lives in Rust

function Overview() {
  const balance = signal(ledger.add(Portfolio.total()));   // Rust, called at once
  return (
    <View class="gap-2 p-4">
      <Text>Balance: {balance()}</Text>
      <Chart symbol="NSH" range="1M" onSelect={(e) => balance.set(ledger.add(e.price))} />
      <View onPress={() => ledger.upload("https://example.com/ledger")} role="button" class="rounded-lg bg-blue-600 px-4 py-2 active:bg-blue-700">
        <Text class="text-white">Upload</Text>
      </View>
    </View>
  );
}

mount(() => (
  <Window id="main">
    <Overview />
  </Window>
));
```

Each export is documented in TypeScript by the doc comment of the Rust item that names it: a component by its
`#[component] fn` (`Chart`), a module and a class by their struct (`Portfolio`, `Ledger`), and props, events,
functions and members by their own (a setter needs none beside its getter). The `Props` struct's and the event
enum's own doc comments, and those of `impl` blocks, stay in Rust; a doc comment on a `#[module]` or `#[class]`
`impl` block is a compile error, since TypeScript would not show it. Each command that writes `.nsh/types` warns
about an export TSX sees without a doc comment, naming it (`Ledger.add`, `Chart.range`).

TypeScript shows a doc comment up to its first heading. Notes for Rust callers, such as what `&self` borrows or
why a function takes `cx`, go under a heading, `# Rust` (or rustdoc's `# Panics`, `# Examples`), and stay in the
Rust docs:

```rust
/// Puts `text` on the clipboard; resolves with the number of characters copied.
///
/// # Rust
///
/// Taking `cx` makes it an op, run in order with the UI changes TS made before it.
pub fn copy(text: String, cx: &mut ModuleCx) -> u32 {
    let count = text.chars().count() as u32;
    cx.set_clipboard(text);
    count
}
```

Props are the fields of the component's `Props` struct and events the variants of its `Event` enum (`onSelect`),
both in camel case. Rust code places the same component with its constructor, a setter per prop and a listener
method per event: `chart().symbol("NSH").range("1M").on_select(move |price: &f64| last.set(*price))`. A Rust component's own content, events and state stay in Rust; TSX passes props in and hears
events. A prop of the wrong type (`level={1.5}` for a `u32` prop) is a warning, as on a built-in element: the
prop keeps its value and the rest of the component renders.

A function or a member runs the way its Rust signature says. One that is not `async` runs inside the TSX call and
returns its value (`Portfolio.total()` is a number, `ledger.balance` a property): it computes and keeps state. An
`async fn` returns a Promise and runs as a task with NSH's services (`fetch`, `timer`, dialogs). A module function
taking `cx: &mut ModuleCx` reaches the platform in order with the UI (a toast, the status bar) and may `spawn` a
task, which runs to its end. A component's ref method also reaches the platform in order with the UI; their return type decides what TSX gets: one returning `()` gives `void`, with no reply
(TSX calls it and moves on); one returning `Result<(), E>` gives `Promise<void>`, which rejects with the `Err`'s
message (the call runs with the UI's changes, after the TSX call returned, so the Promise carries its error; one
nobody awaits or catches is logged as an [unhandled rejection](./dev-server-and-debugging.md#logs)); one
returning a value gives `Promise<T>`. Arguments and results are typed from the signature: numbers, strings, `Option`, `Vec`, your
`#[derive(JsObject)]` structs and `#[derive(PropEnum)]` enums, instances of your classes, and TSX functions
(`Callback<A, R>`, which Rust calls at once inside a call or from a task, or later with `post` and `call_async`; TS sees
`(value: number) => void` for a `Callback<f64>`, and `#[args(balance)] listener: Callback<f64>` names the argument,
`(balance: number) => void`), and any TSX object Rust keeps as it is (`JsHandle`, TS `object`: stored in a field or
a map, compared by identity and given back to TSX as the same object), and your classes themselves (`Constructor`,
TS `Function`: `getRequiredService(I18nService)` tells Rust which class TSX named). Where those types are looser than
TS should be, `#[ts("<T>(token: { readonly prototype: T }): T")]` on the member or function declares its TypeScript
signature as written, generic ones too; the compiler checks that it names the Rust parameters, in their order.
`#[class(generic = "T")]` on a class's struct declares the class generic (`class ServiceToken<T>`), so a
`ServiceToken<I18nService>` is no `ServiceToken<Clock>`; Rust's own types name it `ServiceToken<any>`. A type the
signatures share is the set's too: `registry.ts_alias(TsAlias { name: "ServiceKey<T>",
ts: "{ readonly prototype: T } | ServiceToken<T>", doc: "…" })` exports `type ServiceKey<T>`. A trait marked
`#[interface]` is a
TypeScript interface that TSX objects implement for Rust: the set declares `export interface Startable` (a method per
trait method, optional where the trait has a default body, `#[getter]` methods as `readonly` properties), and Rust
calls such an object through the trait's stand-in `JsStartable`, taken as an argument or made from a kept object
(`JsStartable::new(handle)`); register it with `registry.interface::<JsStartable>()`. A method that is not `async`
runs the TSX method at once inside a call from TSX (outside one, a method returning `()` runs in TSX's next turn),
a `#[getter]` and a method returning a value run at once there and also from a task or a component, as a
`Callback`'s `call` does (`handle.get::<T>("name")` reads any property of a kept object the same way), an `async fn` awaits it (a value as well as a Promise: `#[ts("(): boolean")]` on it declares
`isInitialized(): boolean`), and what TSX throws is the `Err` of a method returning a `Result`. Another crate adds
methods to your class with `#[class_extension(AppBuilder)]` on an `impl` block of a type of its own: each function
taking `this: Instance<AppBuilder>` is a method of `AppBuilder` in TSX (`builder.addI18n((o) => …)`), on every
instance once a UI set the app serves registers it with `registry.class_extension::<I18nBuilder>()`, and the class's
declaration lists it. A function that starts listening is named `on(event, listener)` and returns `Stop`
(`Stop::new(|| …)`), which TSX gets as a function that stops it (`() => void`); it runs once, when TSX calls it or
when what called `on` goes (a component, or the module's run under hot reload). An event's handler gets one object: a variant's value is its field `value`, which
`#[args(price)]` on the variant names (`onSelect({ price })`), and `#[args(open, reason)]` names the fields of a
variant of several. An argument of
the wrong type throws a `TypeError` in the call, or rejects the Promise of one that returns a Promise; an `Err`
throws (or rejects) with its message. A class's object owns its Rust value: it is freed when the object is collected, or at
once with `ledger.dispose()` (also `using ledger = new Ledger()`). Name the TSX entry to run it, `nsh run App.tsx` or `nsh package App.tsx --target …`: TSX edits are hot
updates, Rust edits rebuild and restart the app. The CLI bundles and compiles the TSX itself, knowing your crate's
exports from its description; the development hosts and `nsh test`'s headless runner are built with your crate and
QuickJS.

`examples/rust-exports` in the repository is the reference for exporting: a small TSX app whose crate exports one
component (props required, defaulted and optional, an event, children), one module (a function of each kind) and
one class (a constructor, methods, a getter and a setter, a static, an `async` member, another instance as an
argument, a callback Rust posts to, `dispose()` and `using`), each with a short doc comment, and tests, in Rust and
in TypeScript (`App.test.tsx`), that press through the app and check what each one shows.

`examples/gallery-rs` in the repository is a complete Rust app: every demo is Rust, `nsh run examples/gallery-rs
--target web` (or `ios`, `android`, …) runs its root, `nsh test examples/gallery-rs` runs its tests headless, and
`cargo run -p gallery-native` starts it on the desktop backend.

### Render functions and the app's classes

A component draws content of the app's for values it has (a row of its data, a code block of a document) with a
render function: a prop `Option<Renderer<T>>`, in TypeScript `(value: T) => JSX.Element`. The component calls
`render(key, value)` where the content goes and gets a view it styles and places as any other (inside a `text(..)`, an
inline view). The content is kept per key while the value stays equal, and rendered again when it changes. A Rust
parent passes a closure to the prop's setter (`quote().render_badge(|symbol| ..)`), which makes the
`Renderer` of it.

Styles in a component are typed; the app's Tailwind classes reach one of its parts through a prop of classes and
`.app_class(..)` on that part's element. They apply after the element's own styles, with the app's theme, `dark:` and
the states, as `class` on an element does.

```rust
/// A quote: its symbol, then content of the app's.
#[derive(Clone, Copy, PartialEq, Props)]
pub struct QuoteProps {
    /// The symbol.
    pub symbol: Prop<SharedString>,
    /// Tailwind classes of the symbol's text.
    pub symbol_class: Prop<Option<SharedString>>,
    /// Content of the app's after the symbol (a change, a badge).
    pub render_badge: Prop<Option<Renderer<SharedString>>>,
}

/// A quote of a symbol.
#[component]
pub fn Quote(props: QuoteProps) -> impl IntoElement {
    view()
        .flex_row()
        .items_center()
        .gap_2()
        .child(text(props.symbol).app_class(props.symbol_class))
        .child(dynamic(move || {
            props.render_badge.get().map(|r| r.render("badge", props.symbol.get()).flex_1())
        }))
}
```

```tsx
<Quote
  symbol="NSH"
  symbolClass="text-lg font-semibold"
  renderBadge={(symbol) => <Text class="text-green-600">{`${symbol} ▲ 2.4%`}</Text>}
/>
```

`TextView` in `nsh/base` is built this way: its `renderCodeBlock`, `renderMath`, ... are render functions, and its
`classes` are the app's classes by part ([TextView](../elements/text-view.md)).

## Testing

A Rust app's tests run it headless, in `cargo test` or in `nsh test`, with the same driver: on the real engine,
without a window, with display frames at 60 Hz, so timers, tasks and animations run as on screen. The driver starts
the app, keeps a model of the views it shows and takes steps (`press`, `type_text`, `submit`, `scroll`, `wait_for`)
on views named by selectors (a text, an accessibility label or a test id; `text:`, `label:`, `id:`); a step that
cannot be taken fails with the texts on screen.

In `cargo test`, `nsh_testing::Headless` (nsh-testing's default features, without QuickJS) runs the root
(`app.screen()`: the texts on screen, the commands it sent); `EngineConfig::new` is a phone-sized engine with nothing
else set. `nsh test` runs TypeScript tests ([Testing](./testing-and-trace.md)) in a headless runner built with your
crates, where `open(".")` starts a Rust app's root:

```toml
[dev-dependencies]
nsh-engine = "0.1"
nsh-testing = "0.1"
```

```rust tabs
// tests/app.rs: cargo test
use nsh_engine::{EngineConfig, Root};
use nsh_testing::Headless;

#[test]
fn a_tap_counts() {
    let mut app = Headless::start(EngineConfig::new(Root::of::<my_app::App>())).unwrap();
    app.wait_for("Count: 0").unwrap();
    app.press("Tap").unwrap();
    app.wait_for("Count: 1").unwrap();
}
```

```tsx tabs
// App.test.tsx, next to nsh.json: nsh test
import { expect, open, test } from "nsh/test";

test("a tap counts", async () => {
  const app = await open(".");
  await app.press("Tap");
  expect(app.texts()).toContain("Count: 1");
});
```

Text is laid out with an estimate of its width (every character `0.55 ×` the font size) unless the test starts the
app with `Headless::start_with_text_engine`, which takes a function making the platform's text engine on the engine's
thread (`nsh_platform_macos::CoreTextEngine`, `nsh_platform_windows::DWriteTextEngine`), so text measures as it does on
screen. `app.screen().layout_nodes()` returns the views on screen in tree order as layout placed them (`LayoutNode`:
kind, test id, parent, bounds in the root's points before transforms, whether it is hidden or clips, a scroll view's
axis and content size in `scroll`, a text view's text and the box it was laid out in in `text`), so a test can check
that nothing passes its parent, is cut by a view that clips, or is too wide for its text. Both are Rust API of
`nsh_testing`, for `cargo test`.

A web app's routing is tested on its page: `Headless::start_at_page(config, "https://example.test/app/")` starts the
app on the web at that address, and `app.browser()` is the browser around it, with the history the web keeps (an
entry per page a stack pushes and per open dialog, the app's `set_app_url_with(url, HistoryBehavior::Push)` addresses)
and the user's moves through it: `back()`, `forward()`, `go(delta)` and `type_address("#inbox")`, which the app hears
as on the web (`next_app_url_change`, `next_url_scheme_open`); `entries()`, `index()` and `url()` read the history.

```rust
let mut app = Headless::start_at_page(config, "https://example.test/app/").unwrap();
app.press("Message").unwrap(); // pushes a page and sets `?m=1`
assert_eq!(app.browser().url(), Some("https://example.test/app/?m=1"));
app.browser().back().unwrap(); // pops the page
app.browser().type_address("#inbox").unwrap(); // an `Address` change
```

A TSX entry is built with `nsh-testing`'s feature `bundle` as `nsh run` builds it, against the UI sets its hosts
serve: NSH's, and each crate's `registry()`, which `#[native_module]` makes:

```toml
[dev-dependencies]
nsh-testing = { version = "0.1", features = ["bundle"] }
nsh-base = "0.1"
```

```rust
#[test]
fn the_module_formats_money() {
    let sets = vec![nsh_base::registry(), my_app_native::registry()];
    let mut app = nsh_testing::tsx("../App.tsx", sets).unwrap();
    app.wait_for("Formatted at once: $1,234.50").unwrap();
}
```

`nsh_testing::compile_tsx` builds the entry once for several tests, and `nsh_testing::start` hands the
batches to a test that keeps its own model of the screen. `examples/rust-exports` tests its TSX entry this way;
`examples/gallery-rs` tests its Rust root in TypeScript, a test file for about each demo.

## Theme

The look of an app is the app's own: NSH provides the primitives and the unstyled base components of `nsh_base`, and
your crate is the styled layer on top, the app's own component library ([Three layers](./architecture.md#three-layers)). Rust components take their colors, corner radius and fonts from a theme, `theme()` from
`nsh_base`, so one theme document restyles every component of the app. A binding such as
`.bg(move || theme().primary)` follows every change of the theme natively, with no render.

The theme has the design tokens of [shadcn/ui](https://ui.shadcn.com/docs/theming), and its default is shadcn's
`neutral` theme, a black-and-white palette with a 10 pt corner radius. To use your own, set `"theme"` in `nsh.json`
to the path of a theme document, relative to `nsh.json`, or to the document inline; it replaces the default whole.
To change a few tokens of the theme and keep the others, override them with a patch instead
([below](#changing-tokens-while-the-app-runs)):

```json
{
  "name": "My App",
  "rust": ".",
  "theme": "brand-theme.json"
}
```

A theme document is JSON: each token with its `kind` and its `value`, the modifiers whose contexts change values
(its light and dark appearance among them), and the roles NSH's own parts read:

```json
{
  "tokens": {
    "violet-9": { "kind": "color", "value": "#7c3aed" },
    "violet-4": { "kind": "color", "value": "#a78bfa" },
    "primary": { "kind": "color", "value": "{violet-9}" },
    "primary-foreground": { "kind": "color", "value": "#f5f3ff" },
    "ring": { "kind": "color", "value": "{primary}" },
    "up": { "kind": "color", "value": "#16a34a" },
    "radius": { "kind": "number", "value": 8 },
    "font-sans": { "kind": "font", "value": "Inter, sans-serif" }
  },
  "modifiers": {
    "colorMode": {
      "default": "light",
      "contexts": {
        "light": {},
        "dark": { "primary": "{violet-4}", "primary-foreground": "#2e1065", "up": "#4ade80" }
      }
    }
  },
  "resolutionOrder": ["colorMode"]
}
```

- A token's `kind` is what it holds, whatever its name: `color` (`#rgb`, `#rrggbb`, `#rrggbbaa`), `number` (points,
  or a plain number), `font` (a font family list: the first family that is not a generic one is used, and a generic
  first family, `system-ui` or `sans-serif`, is the system font), `string`, `boolean`, `duration` (`"150ms"`),
  `easing` (`[0.2, 0, 0, 1]` or `ease-out`), and the compounds `typography`, `shadow`, `gradient`, `blur`, `border`
  and `transition`. A value may be another token, `"{violet-9}"`: references resolve after everything else, so a
  change of `violet-9` reaches `primary` and `ring`.
- **Light and dark.** A token holds one value. The theme's dark values are the `dark` context of its light/dark
  modifier, `colorMode` above, and `set_modifier("colorMode", "dark")` shows them (below). The appearance (`nsh.json`'s
  `"appearance"`, the system's) decides `dark:` classes, `dark()`, `color(..)` and the colors given per appearance
  (`AdaptiveColor::rgb(0xffffff, 0x0d1117)`), never a token's value.
- **Other modes.** A brand, a density or a contrast is a modifier too ([Modifiers](#theme-documents-and-typed-keys)),
  and `"resolutionOrder"` lists the modifiers in the order their contexts apply, a later one winning.
- **Gradients, shadows and text styles.** A `gradient` token is a `Gradient` (`tokens().gradient("hero")`), a `shadow`
  token its layers (`tokens().shadow("shadow-raised")`), and a `typography` token a `Typography`, which
  `.typography(move || tokens().typography("text-title").cloned().unwrap_or_default())` sets on a text whole (size,
  line height, letter spacing, weight and family). `.adaptive_gradient(..)` and `.adaptive_shadow(..)` take one per
  appearance: `AdaptiveShadow::new(light, dark)` of two tokens' layers.
- **Your own tokens.** Any other name is a token of the app, as a variable in Tailwind's `@theme` is: `"up"` above is
  `token("up")` or a typed key's `get()` in Rust ([below](#theme-documents-and-typed-keys)), `bg-up` / `text-up/70` in
  classes and `token("up")` in TSX ([Theme tokens](./tailwind.md#theme-tokens)). A number such as `"radius-card"` is
  `TokenKey::<Points>::new("radius-card").get()` and `rounded-(--radius-card)`. Each follows its token where it is
  read; `theme().color(name)` reads the tokens the theme was made of and does not follow a token no role reads.
- A document never stops the app: what it cannot use (a value that does not fit its kind, a reference to no token) is
  left out and logged (target `nsh::theme`), and the rest applies. The runtime refuses a shadcn theme file of the old
  format: `Root::theme` and `set_theme` report `legacy-format` and activate nothing, and the theme stays.
  [`nsh theme convert`](./cli.md#nsh-theme) writes such a file as a theme document; `nsh build`, `nsh dev` and
  `nsh run` warn of a `"theme"` in `nsh.json` of the old format (`legacy-format`) and leave it out.
- `nsh run` and `nsh package` hand the theme to the app's root, `Root::theme(json)`, so it is read as a TSX app's is
  and is in the first frame; the `cargo run` binary that `nsh init` writes does the same with `nsh.json`'s `"theme"`.
  A root you make yourself (a test's `EngineConfig::new(Root::of::<App>())`) takes one with
  `.theme(include_str!("../brand-theme.json"))`, and overrides with `.theme_overrides(..)`.

### Changing tokens while the app runs

The app's overrides are one patch over the theme: the entries of its root's `Root::theme_overrides`, then each
`update_tokens(patch)`. To change a few tokens and keep the others, pass just those; `reset_tokens` takes the names it
lists out of the patch, back to the theme's values; `set_theme` makes another document the app's theme:

```rust
use nsh_core::{element::set_modifier, prelude::*};

update_tokens(Patch::new().value("primary", Hsla::from(rgb(0xe11d48)))); // only `primary` changes
reset_tokens(["primary"]); // the theme's primary again
set_modifier("colorMode", "dark"); // the theme's dark values
set_theme(Some(include_str!("../high-contrast.json"))); // another theme document
set_theme(None); // `nsh.json`'s again
```

- A change applies in order with the app's other actions, and all of a turn's theme changes resolve once. What reads
  a changed token (`theme()`, a class, `token()` in TSX) follows in the same frame, and the platform's own controls
  with it.
- An update replaces the patch's entry for the same token, so a thousand updates of one token are one entry. An
  override wins over a modifier's context: update `radius-card` to 12, pick a compact density, and it stays 12. An
  entry the theme does not declare, or of another kind than its token, is logged and left out (and applies again
  under a theme that declares it). `Patch::new().role("popover", "surface")` maps a role.
- `reset_tokens(names)` takes each name out of the patch, a token's override and a role's mapping alike, so the
  theme's value (or the picked context's) is back and stays across modifier switches; `reset_all_tokens()` empties
  the patch, `Root::theme_overrides`' entries included.
- `set_theme(Some(json))` returns what it could not use of the document. A text that is no theme document is refused
  and the theme stays. Another theme keeps the modifier contexts picked that it has, and the overrides.
- A synchronous `#[module]` function does the same with `cx.update_tokens(..)`, `cx.reset_tokens(..)`,
  `cx.reset_all_tokens()`, `cx.set_modifier(..)` and `cx.set_theme(..)` of its `ModuleCx`. TSX:
  [`updateTheme` and `resetTheme`](../modules/nsh.md#updatetheme-resettheme).
- Inside any synchronous call from JS (a `#[class]` member, a class extension's method, a module function),
  `set_modifier`, `set_color_scheme`, `update_tokens`, `reset_tokens` and `reset_all_tokens` go with the ops of the
  call's turn, after what JS sent before the call, as TSX's `setModifier` and `updateTheme` do: a builder method
  that picks the app's theme context before `mount` is in the first frame. `set_theme` goes through a module
  function's `cx.set_theme(..)` or TSX's `setTheme`.
- TSX's `colorScheme()` follows `set_color_scheme` wherever Rust calls it, as it follows `setColorScheme`: as a
  synchronous call from JS returns, and in the turn after a task or a component sets it. `Appearance::System` shows the
  system's scheme again.

### Theme documents and typed keys

A design system with a token structure of its own (surfaces by level, an action color, a card radius) ships its
tokens as a **theme document** whose tokens also say their place in the designer's tree and their doc, and whose
roles map NSH's own parts onto them. The theme document is the app's theme in place of nsh-base's shadcn theme; an
app with none keeps the shadcn theme above.

```json
{
  "tokens": {
    "surface-raised": { "kind": "color", "value": "#ffffff", "path": "surface.raised", "doc": "Cards and sheets." },
    "surface-overlay": { "kind": "color", "value": "#ffffff", "path": "surface.overlay", "doc": "Popovers and menus." },
    "action": { "kind": "color", "value": "#4f46e5", "doc": "The main action." },
    "radius-card": { "kind": "number", "value": 14, "path": "radius.card", "doc": "Cards' corners." }
  },
  "modifiers": {
    "colorMode": {
      "default": "light",
      "contexts": {
        "light": {},
        "dark": { "surface-raised": "#18181b", "surface-overlay": "#27272a", "action": "#818cf8" }
      }
    }
  },
  "resolutionOrder": ["colorMode"],
  "roles": { "popover": "surface-overlay", "primary": "action" }
}
```

- A token's name is the one classes, `{…}` references and `token()` use, and says nothing about its kind: a number
  named `radius-card` is read by `rounded-card` and `rounded-(--radius-card)` as any number is.
- `path` is the token's place in the designer's tree (`surface.raised`), and `doc` its description, which
  `.nsh/types/nsh/tokens.d.ts` shows on `token()`. A path names one token: a second token at the same path is
  left out and reported.
- A theme document has these sections: `name`, `tokens`, `modifiers`, `resolutionOrder` and `roles` (and `$schema`,
  for an editor). Another is reported and left out.
- `"roles"` maps the roles NSH's own parts draw with onto the document's tokens (below).

The UI set registers its document in its `#[native_module]` function, and `theme_keys!` makes a typed key of each
token it declares, in modules by the token's path:

```rust
use nsh_core::prelude::*;

#[native_module("ds/native")]
fn native(registry: &mut Registry) {
    registry.theme_document(include_str!("../theme.json"));
}

pub mod keys {
    nsh_core::element::theme_keys!("theme.json");
}

view()
    .bg(move || keys::surface::RAISED.get().unwrap_or_default())
    .rounded(move || px(keys::radius::CARD.get().unwrap_or_default()))
    .p_4()

update_tokens(Patch::new().key(keys::ACTION, rgb(0xe11d48).into()));
reset_tokens([keys::ACTION.name()]); // the theme's action again
```

- A key is a `TokenKey<V>`: its token's name with the type of its value. A color is an `Hsla`; a number an `f32`,
  points or a plain number (`px(..)` makes it a length, as above); a font an `Arc<str>`; a string a `String`; a
  boolean a `bool`; a duration a `std::time::Duration`; an easing a `CubicBezier`; a text style a `Typography`
  (`font_family`, `size`, `line_height`, `letter_spacing`, `font_weight`); shadows an `Arc<[BoxShadow]>`; a gradient a
  `Gradient`; a blur a `Blur`, a border a `Border` and a transition a `TransitionToken`. Its doc is the token's.
- `key.get()` reads the token where it is used: the nearest [`ThemeScope`](../modules/nsh.md#themescope)'s. It is
  reactive, and outside a scope runs again only when that token changes. `tokens().key(key)` reads it from tokens in
  hand, and `tokens().get_as::<V>(name)` reads a token by name, with an error that says whether it is missing or of
  another kind.
- `Patch::new().key(key, value)` writes a token typed: hand the patch to `update_tokens`.
- `theme_keys!` reads the document when the crate builds, relative to its manifest, and builds the crate again when it
  changes. Path segments become modules in snake case and keys in upper snake case (`type-scale.gutter`:
  `type_scale::GUTTER`); a token without a path is named after its name (`ACTION`).
- `tokens()` says what the active document declares: each name's kind (`kind_of`), path (`path_of`) and doc
  (`doc_of`), the token at a path (`name_at`) and every name (`names()`).
- Code that does not know the app's names, such as `nsh_base`'s components, reads roles instead.

**Roles.** NSH's own parts draw with roles, constants of the crate that draws with them (`nsh_base::role`: `POPOVER`,
`PRIMARY`, `BORDER`, `RADIUS`, `FONT_SANS`, …; [Theme roles](../modules/nsh-base.md#theme-roles)). A role is a name
and the kind of token it reads, in its type: `Role` reads a color (an `Hsla`), `NumberRole` a number, `FontRole` a
font, and `Role<Typography>`, `Role<Arc<[BoxShadow]>>` and the like the other kinds. A document's `"roles"` maps
roles onto its tokens, a token of the kind the role reads, so `nsh_base`'s `theme()` fields and components, the tab
bar, the platforms' menus and alerts, and the default font draw with the document's tokens: above, `theme().popover`
is the design system's `surface-overlay` and `theme().primary` its `action`. Without a mapping a role reads the token
of its own name. A token may play several roles (`"card": "surface", "popover": "surface"`): a design system with one
surface for cards and popovers maps both onto it, and both follow every change of it. A role is played by one token.

- A role resolves in the active document alone, `nsh_base`'s as any library's: a document that neither maps one of
  nsh-base's roles nor has a token of its name gives it nothing, and `theme()` draws that color transparent and the
  `radius` as 0. nsh-base's default document is a theme only while it is the active one.
- A mapping onto a token the theme does not have, or of another kind than the role reads, is reported and left out,
  and the role reads what it would without it (a patch's mapping falls back on the document's).
- `role(role::POPOVER)` reads a role where it is used, typed (`Option<Hsla>` for a color's), and outside a
  [`ThemeScope`](../modules/nsh.md#themescope) runs again only when its token or its mapping changes; `tokens().role(..)`
  reads it from tokens in hand. `theme()` reads its fields the same way: what reads it runs again when one of its
  roles changes, and not for a token none of them reads.

A crate with components of its own declares its roles, and lists them in its registry, mapped by a theme or not, so
the toolchain and the theme's checks know them: `registry.roles(role::all())`, where

```rust
pub mod role {
    use nsh_core::element::{NumberRole, Role};

    nsh_core::roles! {
        /// A banner's surface.
        pub BANNER: Role = "banner" required,
        /// How round a chip is.
        pub CHIP_RADIUS: NumberRole = "chip-radius",
    }
}
```

writes the constants with `all()` beside them, each with its doc and kind. `required` marks a role every theme should
map: a theme that does not is warned of when it loads. Two sets that list one role with different kinds keep the
first, with a warning. `nsh/base` lists its own: 48 roles, none required.

**One document at a time.** The app's document (`nsh.json`'s `"theme"`, `Root::theme`, or `set_theme`'s) is the
theme; without one, the first UI set's that registers one; without any, nsh-base's default. Documents are never
merged, and a token of a document that is not active is read nowhere: an app that adds tokens of its own to a design
system's (`odds-up` for a betting app) ships one document with both. A document that says what it cannot (a kind
there is not, a value of another kind, a role mapped onto a token of another kind) loads with its good entries and
reports the rest.

**The app's overrides.** A patch, `Root::theme_overrides(json)` on the app's root, changes tokens of the theme by
name, and its `"roles"` maps roles onto other tokens:

```json
{
  "values": { "surface-overlay": "#fafafa", "action": "#e11d48", "radius-card": 12 },
  "roles": { "warning": "status-caution" }
}
```

A name the theme does not declare, or a value of another kind than its token's, is a warning and is left out. The
overrides win over every modifier's context, and an embedding app's overrides win over the app's.

**Modifiers.** A theme's modes (its light and dark values, a brand, a density, a contrast) are its `"modifiers"`:
each with its `default` and its `contexts`, each context the token values it changes, and `"resolutionOrder"` the
order they apply in ([`setModifier`](../modules/nsh.md#setmodifier-modifier-modifiers)). The tokens are the
document's values with each modifier's picked context over them, then the overrides, then references.
`set_modifier("brand", "forest")` picks a context in order with the app's other actions (from the app's first turn,
so a pick made while the root is built is in the first frame); a modifier or context the theme lacks is logged and
changes nothing. `modifier("brand")` is the one picked now (reactive) and `modifiers()` lists them with their
contexts and defaults, as `tokens().modifiers()` does. `theme_keys!` makes an enum of each modifier's contexts in
`keys::modifiers`, so the compiler checks the names:

```rust
use keys::modifiers::Brand;

Brand::Forest.set(); // set_modifier("brand", "forest")
let forest = Brand::current() == Some(Brand::Forest); // reactive

// A part of the app in the forest brand and high contrast, whatever the app picks.
theme_scope()
    .modifiers(Some(ScopeModifiers::from(Brand::Forest).and(HighContrast::On)))
    .child(preview())
```

The app's picks are its own: another theme (`set_theme`, a hot reload of the theme file) keeps each context the app
picked where the new theme has it, and the others go back to their defaults. A `ThemeScope`'s `appearance` changes
only its color scheme; it shows the theme's dark values when its `modifiers` also pick `colorMode`'s `dark`.

**The toolchain.** `nsh build` and `nsh dev` learn the documents from the app's crates and its theme: classes
name their tokens (`bg-surface-raised`, `rounded-card`), and `.nsh/types/nsh/tokens.d.ts` types `token()` by kind, with
the docs ([Theme tokens](./tailwind.md#theme-tokens)).

## Several crates

An app's Rust code can be split into crates, each imported by its own specifier: `"rust"` takes a list of crate
paths, and each crate in it has its own `#[native_module]` function.

```json
{
  "rust": ["native/charts", "native/storage"],
  "root": "App"
}
```

```tsx
import { Chart } from "app/charts";        // native/charts: #[native_module("app/charts")]
import { Store } from "app/storage";       // native/storage: #[native_module("app/storage")]
```

Every runner and host links all of them, and `.nsh/types` declares each specifier. Crates share code through Cargo
path dependencies (`shared = { path = "../shared" }`): a crate of company components can be used by several crates
and listed by several apps, and only the crates listed in `"rust"` export to TSX. Each listed crate has a package
name and a specifier of its own; `nsh` reports a repeated one with the two paths that share it. A Rust app's
`"root"` is a component of the first crate listed. During `nsh run` and `nsh dev`, a change to any of them, or to a
crate they depend on by path, rebuilds the app and restarts it.

## Browser APIs on the web

On the web, a crate can call the browser's APIs (a WebSocket, `IndexedDB`, …) through wasm-bindgen and `web-sys`;
`nsh` builds the glue they need with the runtime. See [Web](./web.md#browser-apis-from-rust).
