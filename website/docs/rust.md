# Building with Rust

Native Shell apps are written in Rust, in TSX, or in both. All three run on the same engine: the reactive graph, the
renderer, Taffy layout and the native modules (navigation, dialogs, the keyboard, the status bar) are Rust in every case, and every platform renders with its
own UI. What differs is the language of your own code, and with it whether the app carries a JavaScript VM.

| | Rust | TSX | Rust with TSX |
|---|---|---|---|
| Your UI, state and handlers | Rust | TSX on QuickJS | Rust components and modules, TSX screens that use them |
| The app runs | the engine and your crate only, on every platform and in the browser | QuickJS and the engine (in the browser, its JavaScript engine) | QuickJS and the engine, with your crate (in the browser, its JavaScript engine) |
| Suits | Medium and large apps with demanding business logic | Apps and modules delivered at run time, quick iteration | A Rust core with parts that change often |
| Edits | Rebuild and restart | Hot updates | Hot updates for TSX, rebuild and restart for Rust |
| Start | `nsh init my-app --template rust` | `nsh init my-app --template ts` | `nsh init my-app --template mixed` |

## Choosing

**Rust** suits apps whose business logic is large and demanding: trading, editors, data-heavy tools. You get Rust's
type system and compile-time checks across the whole app, the crates.io ecosystem, native performance for your own
code (not only for NSH's), and headless tests of the real UI with `cargo test`. The app is Rust and native code from
start to end: no JavaScript VM ships with it or runs in it, on iOS, Android, macOS, Windows, Linux, GPUI and the web.
Components are functions that run once and bind signals to what they show, as in TSX ([Reactivity](./reactivity.md)),
written with typed styles instead of class strings.

**TSX** suits UI that arrives after the app ships: modules a native app loads at run time, generated by a model or
written by another team, delivered as [signed packages](./signed-packages.md) and run in a sandbox the host configures,
with hot updates while you develop.

**Rust with TSX** keeps the Rust core and adds TSX where it pays off: screens, settings, onboarding, experiments,
anything you iterate on with hot updates or deliver at run time as a [signed package](./signed-packages.md). TSX
imports your Rust components and modules like any NSH module, so the two halves meet at typed interfaces. The TSX
runs on QuickJS, which the app then carries.

## An app written in Rust

```sh
nsh init my-app --template rust
cd my-app
nsh run                        # this machine's backend; --target ios, android, web, macos, linux or windows
nsh package --target web       # or ios, ios-simulator, android, macos, linux, windows
```

Build with [huacnlee/cargo](https://github.com/huacnlee/cargo), the Cargo NSH is developed with: a drop-in fork that builds each dependency once for all your
projects and Git worktrees and keeps its build directory under a size limit on its own, with nothing to configure
([Installation](./installation.md#for-apps-written-in-rust)).

`src/lib.rs` holds the app: components, state, handlers, tasks.

```rust
use nsh_base::{button, theme};
use nsh_core::prelude::*;

/// The components available to TSX through `app/native`.
#[native_module("app/native")]
fn native(registry: &mut Registry) {
    registry.register::<App>();
}

#[component]
pub fn App() -> impl IntoElement {
    let count = signal(0_u32);
    let quote = signal(SharedString::from("…"));
    // Async work runs in tasks; requests go through NSH's network stack.
    spawn(async move {
        if let Ok(response) = fetch("https://api.example.com/quote").await {
            quote.set(response.text().into());
        }
    });
    view()
        .flex_1()
        .items_center()
        .justify_center()
        .gap_4()
        .child(text(move || format!("Count: {}", count.get())))
        .child(text(quote))
        .child(
            // nsh_base's unstyled button, drawn with the theme's colors.
            button()
                .px(px(20.0))
                .py(px(12.0))
                .rounded(move || theme().radius)
                .bg(move || theme().primary)
                .active(|s| s.bg(move || theme().primary.opacity(0.9)))
                .on_press(move || count.update(|c| *c += 1))
                .child(text("Tap").text_color(move || theme().primary_foreground)),
        )
}
```

Elements and components are made the same way: a function makes one (`view()`, `text(..)`, `nsh_base`'s
`button()`, your `#[component] fn Chart`'s `chart()`), and its methods set its props, one setter per prop (a value,
a signal or a closure), and its listeners, one method per event. Listeners are closures of their event
(`move |text: &str| ..`), and `move || ..` for an event without data; `.child(..)` takes an element, or an
`Option`, a `Vec`, an array or an iterator of elements (`.child(rows.iter().map(|r| row(r)))`).

`nsh.json` names the root, and `nsh` mounts it:

```json
{
  "name": "My App",
  "rust": ".",
  "root": "App",
  "theme": "theme.json",
  "appearance": "system"
}
```

`"root"` is the component's path in the crate (`App`, `shell::Gallery`; in the first one with
[several crates](#several-crates)); `"theme"` is the [theme](#theme) its components draw with, and `"appearance"` applies to it as it does to a TSX app. With it,
`nsh run` and `nsh package` of the app's directory build the app's own runner for the target, with the root mounted
and no QuickJS linked in:

| Target | What runs |
|---|---|
| macOS, Windows, Linux | The release runner with your crate, in a window; `nsh run` runs a debug build and shows the app's logs in the terminal |
| iOS, the iOS simulator, Mac Catalyst | The iOS runner with your crate, in an app |
| Android | The app's `libnsh.so` with your crate, started by the runtime's activity |
| Web | `nsh.wasm` with the engine and your crate (3.3 MB for the whole Rust gallery, 0.75 MB with brotli); the page mounts the root |

`nsh` builds what your crate needs and nothing more: a small program of your crate and NSH's core that describes its
components and modules to the CLI, which then does the rest itself, and the runner of each target you run or
package. The first build of a new Rust app compiles your crate and NSH's core, about 60 crates. `nsh test` runs
the app's tests headless in a runner of your crate built the same way.

On Linux, your crate selects optional platform features. Enable `webview` on your
`nsh-platform-linux` dependency to use web views; this links WebKitGTK 6.0, which must be installed to build and run
the app. The generated runner inherits that choice through Cargo feature unification.

During `nsh run`, a change to the crate's Rust code builds the runner again and restarts the app; in the browser,
the open page loads the new runtime by itself. `cargo run` starts the same root directly on the desktop backend
(`src/main.rs`), and native apps that embed NSH mount a Rust root with `AppSource::Rust` on the `AppView` of macOS,
Windows, Linux, GPUI and iOS.

Code for every platform, the web included, uses NSH's services: `fetch` for HTTP
([Networking](./networking.md#from-rust-components)), `timer`, `set_timeout` and `set_interval` for waiting,
`nsh_core::time::Instant` and `nsh_core::time::unix_ms()` for the clock. `background` and `blocking` run work on the
native targets' threads.

## Desktop title bars

Rust apps draw their own title bars with `nsh_core::element::desktop`. Set the
window's `title_bar` attribute to `TitleBarStyle::Hidden` with
`current_window().set(..)`, mark the bar's background
with `.window_drag(true)`, and reserve the native window controls' space with
`title_bar()`. Its `top` is the bar's height, and `left` and `right` are the widths
occupied by the system controls. Reading it subscribes to changes, including full
screen. The platform handles window dragging and the user's title-bar double-click
behavior; `.window_drag(false)` keeps a child out of its parent's drag region.

```rust
use nsh_core::{
    desktop::{TitleBarOptions, TitleBarStyle, WindowAttributes, WindowControl},
    element::desktop::{current_window, title_bar},
    prelude::*,
};

fn window_bar() -> impl IntoElement {
    let mut bar = TitleBarOptions::default();
    bar.style = TitleBarStyle::Hidden;
    bar.height = Some(px(42.0));
    let mut attributes = WindowAttributes::default();
    attributes.title_bar = Some(bar);
    current_window().set(attributes);
    view()
        .h(px(42.0))
        .flex_row()
        .items_center()
        .window_drag(true)
        .pl(move || title_bar().left + px(12.0))
        .pr(move || title_bar().right + px(12.0))
        .child(text("My app").flex_1())
        .child(text("Close").window_control(WindowControl::Close))
}
```

A title bar with `TitleBarStyle::Default` restores the system's. A view with
`.window_control(..)` is the window's minimize, maximize or close button: the
platform carries out its press, and a close goes through the window's
`close_on_press`. The `WindowRef` has the window's other requests
(`set_mode`, `minimize`, `set_bounds`, `close`, ...), `window()` opens windows of
the app's own, and the module has the menus (`set_application_menu`,
`popup_menu`) too: [nsh/desktop](../modules/nsh-desktop.md).

## Files and folders

On the desktops, Rust code shows the system's file dialogs and hands local paths to
the system, each answer awaited in a task: `pick_paths` with an `OpenDialog`
(`OpenDialog::files()`, `::folders()` or `::files_and_folders()`), `pick_save_path`
with a `SaveDialog`, `open_path` (the file's default app), `reveal_path` (the item
selected in Finder, File Explorer or the file manager) and `move_to_trash` (where the
item went, when macOS says). The dialogs answer `Ok(None)` when the user cancels and
an error when they cannot show (on Linux without a file chooser portal, and on iOS,
Android and the web, where `open_path`, `reveal_path` and `move_to_trash` answer
an error too). Every request that fails answers its error, never `false`.

```rust
use nsh_core::{
    file_dialog::{FileFilter, OpenDialog},
    prelude::*,
};

fn open_notes() {
    let picked = pick_paths(
        OpenDialog::files()
            .multiple(true)
            .filter(FileFilter::new("Markdown", ["md", "markdown"]))
            .button_label("Open"),
    );
    spawn(async move {
        match picked.await {
            Ok(Some(paths)) => {
                for path in paths {
                    let _ = reveal_path(path).await;
                }
            }
            Ok(None) => {} // Cancelled.
            Err(error) => log::warn!("no file dialog: {error}"),
        }
    });
}
```

## Extending a Rust app with TSX

The crate's `#[native_module("app/native")]` function names what TSX may import: components
(`registry.register::<Chart>()`), modules of functions (`registry.module::<Portfolio>()`, `#[module]` on a unit struct and its `impl`),
classes (`registry.class::<Ledger>()`, `#[class]` on a struct and its `impl`) and assets; the attribute also makes
`pub fn registry()` at the crate's root, the same set for your tests and other Rust code (`my_app_native::registry()`,
next to `nsh_base::registry()`). In a `#[module]` or
`#[class]` `impl`, the `pub fn`s are exported (`pub(crate)` too); functions without a visibility are helpers that
stay in Rust. Their TypeScript
declarations, doc comments included, are generated from the Rust types into `.nsh/types`, so TSX is checked against
them by `nsh check` and your editor:

```rust
/// A price chart.
#[derive(Clone, PartialEq, Props)]
pub struct ChartProps {
    /// The symbol to chart.
    pub symbol: Prop<SharedString>,
    /// The range shown.
    #[prop(default = SharedString::from("1D"))]
    pub range: Prop<SharedString>,
}

#[derive(Event)]
pub enum ChartEvent {
    /// A price was selected.
    #[args(price)]
    Select(f64),
}

/// A price chart; a press selects the last price.
#[component]
pub fn Chart(props: ChartProps, cx: Scope<ChartEvent>) -> impl IntoElement {
    view()
        .h(px(160.0))
        .bg(move || theme().muted)
        .on_press(move || cx.emit(ChartEvent::Select(101.5)))
        .child(text(move || format!("{} · {}", props.symbol.get(), props.range.get())))
}

/// A ledger kept in Rust.
#[class]
pub struct Ledger {
    entries: Vec<f64>,
}

#[class]
impl Ledger {
    /// An empty ledger.
    pub fn new() -> Self {
        Ledger { entries: Vec::new() }
    }

    /// Adds `amount`; the new balance.
    pub fn add(&mut self, amount: f64) -> f64 {
        self.entries.push(amount);
        self.balance()
    }

    /// The balance.
    #[getter]
    pub fn balance(&self) -> f64 {
        self.entries.iter().sum()
    }

    /// Uploads the entries; resolves when the server has them.
    pub async fn upload(this: Instance<Ledger>, url: String) -> Result<(), String> {
        let body = this.with(|l| format!("{:?}", l.entries));
        fetch(HttpRequest::post(url, body)).await.map(|_| ())
    }
}

/// The app's holdings.
#[module]
pub struct Portfolio;

#[module]
impl Portfolio {
    /// The value of the holdings.
    pub fn total() -> f64 {
        1250.0
    }
}
```

```tsx
import { mount, signal, View, Text } from "nsh";
import { Chart, Ledger, Portfolio } from "app/native";   // Rust

const ledger = new Ledger();   // its state lives in Rust

function Overview() {
  const balance = signal(ledger.add(Portfolio.total()));   // Rust, called at once
  return (
    <View class="gap-2 p-4">
      <Text>Balance: {balance()}</Text>
      <Chart symbol="NSH" range="1M" onSelect={(e) => balance.set(ledger.add(e.price))} />
      <View onPress={() => ledger.upload("https://example.com/ledger")} role="button" class="rounded-lg bg-blue-600 px-4 py-2 active:bg-blue-700">
        <Text class="text-white">Upload</Text>
      </View>
    </View>
  );
}

mount(() => <Overview />);
```

Each export is documented in TypeScript by the doc comment of the Rust item that names it: a component by its
`#[component] fn` (`Chart`), a module and a class by their struct (`Portfolio`, `Ledger`), and props, events,
functions and members by their own (a setter needs none beside its getter). The `Props` struct's and the event
enum's own doc comments, and those of `impl` blocks, stay in Rust; a doc comment on a `#[module]` or `#[class]`
`impl` block is a compile error, since TypeScript would not show it. Each command that writes `.nsh/types` warns
about an export TSX sees without a doc comment, naming it (`Ledger.add`, `Chart.range`).

TypeScript shows a doc comment up to its first heading. Notes for Rust callers, such as what `&self` borrows or
why a function takes `cx`, go under a heading, `# Rust` (or rustdoc's `# Panics`, `# Examples`), and stay in the
Rust docs:

```rust
/// Puts `text` on the clipboard; resolves with the number of characters copied.
///
/// # Rust
///
/// Taking `cx` makes it an op, run in order with the UI changes TS made before it.
pub fn copy(text: String, cx: &mut ModuleCx) -> u32 {
    let count = text.chars().count() as u32;
    cx.set_clipboard(text);
    count
}
```

Props are the fields of the component's `Props` struct and events the variants of its `Event` enum (`onSelect`),
both in camel case. Rust code places the same component with its constructor, a setter per prop and a listener
method per event: `chart().symbol("NSH").range("1M").on_select(move |price: &f64| last.set(*price))`. A Rust component's own content, events and state stay in Rust; TSX passes props in and hears
events. A prop of the wrong type (`level={1.5}` for a `u32` prop) is a warning, as on a built-in element: the
prop keeps its value and the rest of the component renders.

A function or a member runs the way its Rust signature says. One that is not `async` runs inside the TSX call and
returns its value (`Portfolio.total()` is a number, `ledger.balance` a property): it computes and keeps state. An
`async fn` returns a Promise and runs as a task with NSH's services (`fetch`, `timer`, dialogs). A module function
taking `cx: &mut ModuleCx` reaches the platform in order with the UI (a toast, the status bar), and so does a
component's ref method; their return type decides what TSX gets: one returning `()` gives `void`, with no reply
(TSX calls it and moves on); one returning `Result<(), E>` gives `Promise<void>`, which rejects with the `Err`'s
message (the call runs with the UI's changes, after the TSX call returned, so the Promise carries its error; one
nobody awaits or catches is logged as an [unhandled rejection](./dev-server-and-debugging.md#logs)); one
returning a value gives `Promise<T>`. Arguments and results are typed from the signature: numbers, strings, `Option`, `Vec`, your
`#[derive(JsObject)]` structs and `#[derive(PropEnum)]` enums, instances of your classes, and TSX functions
(`Callback<A, R>`, which Rust calls at once inside a call, or later with `post` and `call_async`; TS sees
`(value: number) => void` for a `Callback<f64>`, and `#[args(balance)] listener: Callback<f64>` names the argument,
`(balance: number) => void`). A function that starts listening is named `on(event, listener)` and returns `Stop`
(`Stop::new(|| …)`), which TSX gets as a function that stops it (`() => void`); it runs once, when TSX calls it or
when what called `on` goes (a component, or the module's run under hot reload). An event's handler gets one object: a variant's value is its field `value`, which
`#[args(price)]` on the variant names (`onSelect({ price })`), and `#[args(open, reason)]` names the fields of a
variant of several. An argument of
the wrong type throws a `TypeError` in the call, or rejects the Promise of one that returns a Promise; an `Err`
throws (or rejects) with its message. A class's object owns its Rust value: it is freed when the object is collected, or at
once with `ledger.dispose()` (also `using ledger = new Ledger()`). Name the TSX entry to run it, `nsh run App.tsx` or `nsh package App.tsx --target …`: TSX edits are hot
updates, Rust edits rebuild and restart the app. The CLI bundles and compiles the TSX itself, knowing your crate's
exports from its description; the development hosts and `nsh test`'s headless runner are built with your crate and
QuickJS.

`examples/rust-exports` in the repository is the reference for exporting: a small TSX app whose crate exports one
component (props required, defaulted and optional, an event, children), one module (a function of each kind) and
one class (a constructor, methods, a getter and a setter, a static, an `async` member, another instance as an
argument, a callback Rust posts to, `dispose()` and `using`), each with a short doc comment, and tests, in Rust and
in TypeScript (`App.test.tsx`), that press through the app and check what each one shows.

`examples/gallery-rs` in the repository is a complete Rust app: every demo is Rust, `nsh run examples/gallery-rs
--target web` (or `ios`, `android`, …) runs its root, `nsh test examples/gallery-rs` runs its tests headless, and
`cargo run -p gallery-native` starts it on the desktop backend.

### Render functions and the app's classes

A component draws content of the app's for values it has (a row of its data, a code block of a document) with a
render function: a prop `Option<Renderer<T>>`, in TypeScript `(value: T) => JSX.Element`. The component calls
`render(key, value)` where the content goes and gets a view it styles and places as any other (inside a `text(..)`, an
inline view). The content is kept per key while the value stays equal, and rendered again when it changes. A Rust
parent passes a closure to the prop's setter (`quote().render_badge(|symbol| ..)`), which makes the
`Renderer` of it.

Styles in a component are typed; the app's Tailwind classes reach one of its parts through a prop of classes and
`.app_class(..)` on that part's element. They apply after the element's own styles, with the app's theme, `dark:` and
the states, as `class` on an element does.

```rust
/// A quote: its symbol, then content of the app's.
#[derive(Clone, Copy, PartialEq, Props)]
pub struct QuoteProps {
    /// The symbol.
    pub symbol: Prop<SharedString>,
    /// Tailwind classes of the symbol's text.
    pub symbol_class: Prop<Option<SharedString>>,
    /// Content of the app's after the symbol (a change, a badge).
    pub render_badge: Prop<Option<Renderer<SharedString>>>,
}

/// A quote of a symbol.
#[component]
pub fn Quote(props: QuoteProps) -> impl IntoElement {
    view()
        .flex_row()
        .items_center()
        .gap_2()
        .child(text(props.symbol).app_class(props.symbol_class))
        .child(dynamic(move || {
            props.render_badge.get().map(|r| r.render("badge", props.symbol.get()).flex_1())
        }))
}
```

```tsx
<Quote
  symbol="NSH"
  symbolClass="text-lg font-semibold"
  renderBadge={(symbol) => <Text class="text-green-600">{`${symbol} ▲ 2.4%`}</Text>}
/>
```

`TextView` in `nsh/base` is built this way: its `renderCodeBlock`, `renderMath`, ... are render functions, and its
`classes` are the app's classes by part ([TextView](../elements/text-view.md)).

## Testing

A Rust app's tests run it headless, in `cargo test` or in `nsh test`, with the same driver: on the real engine,
without a window, with display frames at 60 Hz, so timers, tasks and animations run as on screen. The driver starts
the app, keeps a model of the views it shows and takes steps (`press`, `type_text`, `submit`, `scroll`, `wait_for`)
on views named by selectors (a text, an accessibility label or a test id; `text:`, `label:`, `id:`); a step that
cannot be taken fails with the texts on screen.

In `cargo test`, `nsh_testing::Headless` (nsh-testing's default features, without QuickJS) runs the root
(`app.screen()`: the texts on screen, the commands it sent); `EngineConfig::new` is a phone-sized engine with nothing
else set. `nsh test` runs TypeScript tests ([Testing](./testing-and-trace.md)) in a headless runner built with your
crates, where `open(".")` starts a Rust app's root:

```toml
[dev-dependencies]
nsh-engine = "0.1"
nsh-testing = "0.1"
```

```rust tabs
// tests/app.rs: cargo test
use nsh_engine::{EngineConfig, Root};
use nsh_testing::Headless;

#[test]
fn a_tap_counts() {
    let mut app = Headless::start(EngineConfig::new(Root::of::<my_app::App>())).unwrap();
    app.wait_for("Count: 0").unwrap();
    app.press("Tap").unwrap();
    app.wait_for("Count: 1").unwrap();
}
```

```tsx tabs
// App.test.tsx, next to nsh.json: nsh test
import { expect, open, test } from "nsh/test";

test("a tap counts", async () => {
  const app = await open(".");
  await app.press("Tap");
  expect(app.texts()).toContain("Count: 1");
});
```

Text is laid out with an estimate of its width (every character `0.55 ×` the font size) unless the test starts the
app with `Headless::start_with_text_engine`, which takes a function making the platform's text engine on the engine's
thread (`nsh_platform_macos::CoreTextEngine`, `nsh_platform_windows::DWriteTextEngine`), so text measures as it does on
screen. `app.screen().layout_nodes()` returns the views on screen in tree order as layout placed them (`LayoutNode`:
kind, test id, parent, bounds in the root's points before transforms, whether it is hidden or clips, a scroll view's
axis and content size in `scroll`, a text view's text and the box it was laid out in in `text`), so a test can check
that nothing passes its parent, is cut by a view that clips, or is too wide for its text. Both are Rust API of
`nsh_testing`, for `cargo test`.

A TSX entry is built with `nsh-testing`'s feature `bundle` as `nsh run` builds it, against the UI sets its hosts
serve: NSH's, and each crate's `registry()`, which `#[native_module]` makes:

```toml
[dev-dependencies]
nsh-testing = { version = "0.1", features = ["bundle"] }
nsh-base = "0.1"
```

```rust
#[test]
fn the_module_formats_money() {
    let sets = vec![nsh_base::registry(), my_app_native::registry()];
    let mut app = nsh_testing::tsx("../App.tsx", sets).unwrap();
    app.wait_for("Formatted at once: $1,234.50").unwrap();
}
```

`nsh_testing::compile_tsx` builds the entry once for several tests, and `nsh_testing::start` hands the
batches to a test that keeps its own model of the screen. `examples/rust-exports` tests its TSX entry this way;
`examples/gallery-rs` tests its Rust root in TypeScript, a test file for about each demo.

## Theme

The look of an app is the app's own: NSH provides the primitives and the unstyled base components of `nsh_base`, and
your crate is the styled layer on top, the app's own component library ([Three layers](./architecture.md#three-layers)). Rust components take their colors, corner radius and fonts from a theme, `theme()` from
`nsh_base`, so one file restyles every component of the app. Each color has a light and a dark value;
when the system switches appearance, a binding such as `.bg(move || theme().primary)` changes color natively, with no
render.

The theme has the design tokens of [shadcn/ui](https://ui.shadcn.com/docs/theming), and its default is shadcn's
`neutral` theme, a black-and-white palette with a 10 pt corner radius. To use your own, set `"theme"` in `nsh.json`
to the path of a theme file, relative to `nsh.json`, or to the theme's content inline:

```json
{
  "name": "My App",
  "rust": ".",
  "theme": "brand-theme.json"
}
```

A theme file is shadcn's `cssVars`, the format of shadcn's themes and registry items, so a theme exported from
[shadcn's themes](https://ui.shadcn.com/themes) or [tweakcn](https://tweakcn.com) works as it is. `light` sets the
values of the light appearance, `dark` those of the dark one, and `theme` those of both:

```json
{
  "cssVars": {
    "theme": {
      "radius": "0.5rem",
      "font-sans": "Inter, sans-serif"
    },
    "light": {
      "primary": "oklch(0.541 0.281 293.009)",
      "primary-foreground": "oklch(0.969 0.016 293.756)",
      "ring": "var(--primary)",
      "up": "#16a34a"
    },
    "dark": {
      "primary": "oklch(0.702 0.183 293.541)",
      "primary-foreground": "oklch(0.283 0.141 291.089)",
      "up": "#4ade80"
    }
  }
}
```

- Your theme is applied over the default theme, so you list only what you change. A value `light` sets and `dark`
  leaves out is used in both appearances.
- Values are written as in CSS. Colors are any CSS color (`#7c3aed`, `rgb(…)`, `hsl(…)`, `oklch(…)`, `white`),
  `color-mix(in oklab, var(--primary) 80%, white)`, or another token of the same appearance, `var(--primary)` (with a
  fallback: `var(--brand, #7c3aed)`). Lengths are `rem` (16 points) or `px` (points). Fonts are font family lists:
  the first family that is not a generic one is used, and a generic first family (`system-ui`, `sans-serif`) is the
  system font.
- **Shadows.** A `shadow-<n>` written as CSS `box-shadow` (`"shadow-raised": "0 1px 2px #0000001a"`, per appearance in
  `light` and `dark`) is a shadow token: `tokens().shadow("shadow-raised")` is an `AdaptiveShadow`, and
  `.adaptive_shadow(move || tokens().shadow("shadow-raised").cloned().unwrap_or_default())` draws it, following theme
  changes and switching with the appearance natively as `.bg(..)` does. `.shadow(layers)` takes static layers, the
  same in both.
- **Numbers per appearance.** A number in `dark` is its dark value (`"dark": { "radius-card": "6px" }`): classes and
  TSX's `token()` follow the appearance, and Rust reads it with `tokens().number_in("radius-card", dark())`
  (`number()` is the light value, the only one of a number the theme gives once). `theme().radius` and
  `theme().number(..)` are light values too: read one that has a dark value with `number_in`.
  `Tokens::set_dark_number` gives one in code.
- **Your own tokens.** Any other name is a token of the app, as a variable in Tailwind's `@theme` is: `"up"` above is
  `theme().color("up")` in Rust, `bg-up` / `text-up/70` in classes and `token("up")` in TSX
  ([Theme tokens](./tailwind.md#theme-tokens)). A number such as `"radius-card": "14px"` is `theme().number("radius-card")`
  and `rounded-(--radius-card)`.
- The bundler checks the theme when it builds: a missing file, invalid JSON or a theme other than `cssVars` fails the
  build with an `nsh.json: theme: …` error.
- `nsh run` and `nsh package` hand the theme file to the app's root, `Root::theme(json)`, so it is read as a TSX
  app's is and is in the first frame; the `cargo run` binary that `nsh init` writes does the same with `nsh.json`'s
  `"theme"`. A root you make yourself (a test's `EngineConfig::new(Root::of::<App>())`) takes one with
  `.theme(include_str!("../brand-theme.json"))`; the UI set that reads themes reads it, so the engine's `ui_sets`
  need `nsh_base::registry()` (the desktops' `run_app` has it already).

### Changing tokens while the app runs

`set_tokens(theme.into())` makes another theme the app's ([Theme tokens](./tailwind.md#theme-tokens)). To change a
few tokens and keep the others, pass just those to `update_tokens`; `reset_tokens` puts the tokens it names back to
the app's theme:

```rust
use nsh_core::prelude::*;

let mut brand = Tokens::default();
brand.set_color("primary", AdaptiveColor::rgb(0xe11d48, 0xfb7185));
update_tokens(brand); // only `primary` changes
reset_tokens(["primary"]); // the app's primary again
```

- A change applies in order with the app's other actions: two updates in one turn both take, the later over the
  earlier. What reads a changed token (`theme()`, a class, `token()` in TSX) follows in the same frame, and the
  platform's own controls with it.
- The app's theme is `nsh.json`'s over the default, or the one `set_tokens` or `setTheme` set last. A name
  `reset_tokens` gives that the theme does not have is removed.
- A synchronous `#[module]` function does the same with `cx.update_tokens(..)` and `cx.reset_tokens(..)` of its
  `ModuleCx`. TSX: [`updateTheme` and `resetTheme`](../modules/nsh.md#updatetheme-resettheme).

### Theme types

A design system with a token structure of its own (surfaces by level, an action color, a card radius) brings its
tokens as a Rust type, a **theme type**: a struct of its tokens that implements `AppTheme` (`nsh_core::element`, also in
the prelude). Components read it typed with `theme_of::<T>()`, as they read `theme()`, and the theme file, classes and
`token()` in TSX name its tokens. A registered theme type is the app's token source in place of nsh-base's shadcn
theme; an app that registers none keeps the shadcn theme above.

A type lists its tokens in `token_specs()`: each a `TokenSpec` with a name, a `TokenKind` (`Color`, `Number`, `Radius`,
`Spacing`, `Text`, `Weight`, `Tracking`, `Leading`, `Blur`, `Font`, `Shadow`), a doc comment and the role it plays.
`write_tokens` and `read_tokens` turn its fields into tokens and back, and `write_patch` writes the fields a patch sets;
each puts its names under `prefix` (`TokenKind::prefixed`), so a type can hold another: in front of a color's or a
number's name (`surface-` and `raised`: `surface-raised`), after a namespaced name's namespace, so its classes still
read it (`radius-card`: `radius-surface-card`, `rounded-surface-card`). `#[derive(AppTheme)]` writes the impl of a
struct's fields:

```rust
use nsh_core::prelude::*;

/// The design system's tokens.
#[derive(Clone, PartialEq, AppTheme)]
pub struct DsTheme {
    /// Cards and sheets.
    #[token(color)]
    pub surface_raised: AdaptiveColor,
    /// Popovers and menus.
    #[token(color, role = "popover")]
    pub surface_overlay: AdaptiveColor,
    /// The main action.
    #[token(color, role = "primary")]
    pub action: AdaptiveColor,
    /// Cards' corners.
    #[token(radius)]
    pub card: f32,
}

impl Default for DsTheme {
    fn default() -> Self {
        DsTheme {
            surface_raised: AdaptiveColor::rgb(0xffffff, 0x18181b),
            surface_overlay: AdaptiveColor::rgb(0xffffff, 0x27272a),
            action: AdaptiveColor::rgb(0x4f46e5, 0x818cf8),
            card: 14.0,
        }
    }
}
```

- Each field is one token, `#[token(<kind>)]`, named after the field in kebab case: `color` and `number` as it is
  (`surface-raised`), a namespaced kind with its namespace, as its classes read it: `radius` (`card`: `radius-card`,
  `rounded-card`), `spacing` (`spacing-*`), `text` (`text-*`), `weight` (`font-weight-*`), `tracking`, `leading`,
  `blur`, `font` (`font-*`) and `shadow` (`shadow-*`). A color is an `AdaptiveColor`, a number an `f32` or `Points`, a
  font family a `SharedString` or `String`, a shadow an `AdaptiveShadow`. `name = "…"` names a token (a namespaced
  kind's name keeps its namespace: `#[token(radius, name = "radius-corner")]`), `role = "…"` maps a role onto it.
- `#[token(nested)]` holds another `AppTheme` type, its names under `<field>-` as above (`surface: Surface` with
  `raised`: `surface-raised`, with `#[token(shadow)] raised`: `shadow-surface-raised`), read as
  `theme_of::<DsTheme>().surface.raised`. A name the tokens lack keeps the inner type's `Default`, not the value the
  outer `Default` gives the field. `#[token(flatten)]` is the same with no prefix; `#[token(skip)]` is no token (the
  field keeps `Default`'s value).
- A number field is its token's light value, as `number()` is: read a dark value with `tokens().number_in("radius-card",
  dark())`, or draw with the class (`rounded-card`), which follows the appearance. `set_theme` writes one value per
  number, so it drops a dark value the theme file gave; `update_theme` changes only the fields its patch sets.
- A field's doc comment is its token's, which `.nsh/types/nsh/tokens.d.ts` shows on `token()`.
- It makes `DsThemePatch`, each field an `Option` (a nested one its type's patch) documented with its token and the
  classes that read it, for `update_theme`.
- These are compile errors at the attribute: a name given twice, empty, or of the wrong form for its kind (only a font
  is `font-*`, a weight `font-weight-*`, and a namespaced kind's name starts with its namespace); a kind that does not
  fit the field (`#[token(radius)]` on an `AdaptiveColor`), an unknown kind, two kinds, or a kind with `nested`,
  `flatten` or `skip`; a role of no name, of another kind of token or mapped twice; `name` or `role` on a field that is
  no token; a second `#[token]`; a nested field named `font…` or `weight…` (its names would read as another kind's:
  `font-…` as fonts, `font-weight-…` as weights), which needs another name; and a generic struct. A type can also
  implement `AppTheme` by hand: its four methods put each name under `prefix` with `TokenKind::prefixed`, and a
  namespaced kind's names keep to its namespace.

A token's name says how theme files and classes read it. A color's name is free (`surface-raised`, `action`); a
number's starts with its Tailwind namespace (`radius-card`, `spacing-gutter`, `text-body`, `font-weight-strong`, or
`tracking-`, `leading-`, `blur-`); a font's starts with `font-` and a shadow's with `shadow-`.

The UI set registers the type in its `#[native_module]` function, and components read it where they draw:

```rust
#[native_module("ds/native")]
fn native(registry: &mut Registry) {
    registry.theme::<DsTheme>();
}

view()
    .bg(move || theme_of::<DsTheme>().surface_raised)
    .rounded(move || px(theme_of::<DsTheme>().card))
    .p_4()

update_theme::<DsTheme>(DsThemePatch {
    action: Some(AdaptiveColor::rgb(0xe11d48, 0xfb7185)),
    ..Default::default()
});
reset_theme::<DsTheme>(); // the app's action again
```

- `theme_of::<T>()` is an `Arc<T>` read from the surface's tokens. It is reactive as `tokens()` is: a binding that
  reads it runs again when the tokens change. It is read once per change of the tokens, per surface, so every binding
  can call it.
- `set_theme(theme)` draws the app with a whole `T`: its names take its values, and every other token stays.
  `update_theme::<T>(patch)` changes the fields the patch sets. `reset_theme::<T>()` puts `T`'s names back to the
  app's theme (`nsh.json`'s over the types' defaults). They apply in order with the app's other actions, as
  `update_tokens` does; a synchronous `#[module]` function has `cx.set_theme(..)`, `cx.update_theme::<T>(..)` and
  `cx.reset_theme::<T>()` of its `ModuleCx`.
- A number field is its token's light value. `set_theme` leaves the dark value of a number whose value it does not
  change, so reading a theme, changing one field and setting it changes that field only:
  `let mut t = (*theme_of::<DsTheme>()).clone(); t.action = red; set_theme(t);`. A number it does change, and one a
  patch sets, is that value in both appearances; give it a dark value again with `Tokens::set_dark_number` and
  `update_tokens`.

**Roles.** NSH's own parts draw with roles (`Role`: `popover`, `primary`, `border`, `radius`, `font-sans`, …;
[Theme roles](../modules/nsh-base.md#theme-roles)). A type maps roles onto its tokens with `TokenSpec::role`, so
`nsh_base`'s `theme()` fields and components, the tab bar, the platforms' menus and alerts, and the default font draw
with the type's tokens: above, `theme().popover` is the design system's `surface-overlay` and `theme().primary` its
`action`.

**Names.** A token's name says what its kind is, as a CSS variable's does: a font's starts with `font-`, a shadow's
with `shadow-`, a weight's with `font-weight-`, and no other kind's with `font-`. Registering a type whose name and
kind disagree, or that declares a name or maps a role twice, panics.

**Several types.** A design system's crate and the app's crate each register their own type: the design system's
tokens, and the app's own beside them (`odds-up` for a betting app). Each reads its own with `theme_of`, and the names
of every registered type merge into one theme. A token name or a role that two types claim panics when the UI sets
are merged, naming both types.

**The theme file.** `nsh.json`'s `"theme"` keeps shadcn's `cssVars` format and sets the types' tokens by name, each
read as its declared kind (a color as a CSS color, a radius as a length). A role's name sets the token the role is
mapped onto: `"primary"` below sets the design system's `action`. `var(--surface-raised)` names a token the file
sets, else the types' default. A name that no type declares, or a value of another kind, is a build warning and is
left out when the app runs. A key that is a role's name, in a section that also sets the token the role is mapped
onto, gives way to that token. An embedding app's theme overrides and TSX's `setTheme` and `updateTheme` read their
files the same way: they leave a name no type declares out, and refuse a value they cannot read.

```json
{
  "cssVars": {
    "theme": { "radius-card": "12px" },
    "light": { "surface-overlay": "#fafafa", "primary": "#e11d48", "odds-up": "#16a34a" },
    "dark": { "surface-overlay": "#27272a", "primary": "#fb7185", "odds-up": "#4ade80" }
  }
}
```

**The toolchain.** `nsh build` and `nsh dev` learn the types from the app's crates: classes name their tokens
(`bg-surface-raised`, `rounded-card`), and `.nsh/types/nsh/tokens.d.ts` types `token()` by kind, with the doc comments
([Theme tokens](./tailwind.md#theme-tokens)).

**nsh-base's theme.** `nsh_base::Theme` is a theme type too, left unregistered so it stays the default source:
`theme()` is `theme_of::<Theme>()`, and a shadcn app changes some of its tokens with `update_theme::<Theme>(tokens)`,
a patch of `Tokens` by name.

## Several crates

An app's Rust code can be split into crates, each imported by its own specifier: `"rust"` takes a list of crate
paths, and each crate in it has its own `#[native_module]` function.

```json
{
  "rust": ["native/charts", "native/storage"],
  "root": "App"
}
```

```tsx
import { Chart } from "app/charts";        // native/charts: #[native_module("app/charts")]
import { Store } from "app/storage";       // native/storage: #[native_module("app/storage")]
```

Every runner and host links all of them, and `.nsh/types` declares each specifier. Crates share code through Cargo
path dependencies (`shared = { path = "../shared" }`): a crate of company components can be used by several crates
and listed by several apps, and only the crates listed in `"rust"` export to TSX. Each listed crate has a package
name and a specifier of its own; `nsh` reports a repeated one with the two paths that share it. A Rust app's
`"root"` is a component of the first crate listed. During `nsh run` and `nsh dev`, a change to any of them, or to a
crate they depend on by path, rebuilds the app and restarts it.
